系统架构与选型分析

LiveKit Agents 语音助手 —— 把「实时传输层」和「Agent 编排层」做成一体的工程化主线，兼顾低延迟与高能力上限。

框架 LiveKit Agents 1.1.7 传输 WebRTC SFU 模型 百炼 qwen3-omni-flash-realtime 实测首音频延迟 ~514ms 2026-07-27
TL;DR

六个开源框架实测后，选定 LiveKit Agents 作为工程化主线：浏览器经 WebRTC 接入本地 LiveKit Server，由 Agent Worker 编排后接阿里云百炼 Realtime 一体模型，端到端首音频延迟 ~514ms（其中编排成本 ~260ms）。

它不是最快的（voice-agent / FastRTC 直连约 ~250ms），但是唯一能把工具调用、RAG、多模型混编、电话 SIP 全部做成框架原生能力、并能平滑演进到「双 LLM 终态」的底座 —— 延迟与能力的最佳平衡点。

02

优势与劣势

选型不是选最快的，而是选能力天花板与延迟最平衡的。

✓优势

  • 工程能力天花板高 — 工具 / RAG / SIP / 多方全是框架原生能力，不需要自己造 （voice-agent 直连方案这些都要手写）
  • 生态最活跃 — 六框架实测中社区、文档、商业支持（LiveKit Cloud）都是第一梯队
  • 传输层专业 — WebRTC SFU 自带弱网对抗、自适应码率，浏览器 / 移动端 / 电话全端覆盖
  • 延迟可接受 — ~514ms 在实时对话感知阈值内，且编排成本是一次性固定开销
  • 模型解耦 — 百炼可平替 OpenAI Realtime，协议已打通（含 beta 协议踩坑经验）
  • 可私有化 — 除模型外全栈本地，满足企业内网合规要求

✗劣势

  • 延迟高于直连 — 比 voice-agent 直连百炼（~250ms）多 ~260ms 编排成本 （追求极限延迟的演示场景直连仍最优）
  • 组件多、运维面大 — 需维护 LiveKit Server + Agent Worker + Token 服务三个进程
  • 百炼兼容有坑 — 插件必须锁 1.1.7（≥1.2 静默超时）、metadata 需打补丁，升级需重新验证
  • 学习曲线 — 房间 / 轨道 / job 分发概念比「开一个 WebSocket」复杂
  • 不及管道方案灵活 — 若需逐字控制 STT/LLM/TTS 任意组合，Pipecat 管道更细粒度（但延迟 ~2.1s）

五个开源框架横向实测，LiveKit 是延迟与能力的最佳平衡点。

最大的差异化优势

LiveKit 是唯一把「实时传输层」和「Agent 编排层」做成一体的框架。

别的方案里，WebRTC 传输（弱网对抗、多端适配、电话接入）要自己拼；Agent 编排（打断、工具、状态机）也要自己拼。LiveKit 两边都是生产级现成的，中间用「房间 / job 分发」模型天然咬合。

这让它成为唯一能平滑演进到 双 LLM 终态架构（flash 先出声 + 高推理模型补充）的底座：多模型混编、会话级状态、工具调度都在编排层原生就位 —— 而这正是「高推理能力 + 低延迟」这一核心需求的最终解法。
